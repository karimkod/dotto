# iOS release setup

Status of the iOS pipeline for `com.karimkod.dotto`, and the steps still needed
to get a build onto TestFlight.

## Verified

The iOS target **compiles**. This had never been confirmed before (the previous
dev machine was Windows, so `.github/workflows/ios-release.yml` carried an
"UNVERIFIED / has never been compiled" warning).

- `flutter build ios --release --no-codesign` → `Runner.app`, 25.9 MB
- `flutter analyze` → no issues
- Runs on the iPhone 17 Pro Max and iPad Pro 13" simulators
- Archiving now gets all the way to the signing step and stops only for the
  missing credentials below

Toolchain used: Flutter 3.44.4, Xcode 26.6. Note CI pins Flutter **3.41.9**
(matching `android-release.yml`), which is not the version verified locally.

CI agrees on where the blockage is. The three runs triggered so far (tags
`v1.0.1+2`, `v1.0.1+3`, `v1.0.2+4`) all failed at the same step:

```
Import Apple Distribution certificate
##[error]At least one of p12-filepath or p12-file-base64 must be provided
```

That is the empty `IOS_DIST_CERT_BASE64` secret. Everything before it (checkout,
Xcode select, Flutter 3.41.9 setup, version parsing, `pub get`) succeeds, so the
secrets below are the only thing standing between here and a TestFlight build.

## Project changes made

| Change | Why |
|---|---|
| `DEVELOPMENT_TEAM = P6733MSWNR` on all three Runner configs | Was absent entirely. Without it `xcodebuild archive` fails with "Signing for Runner requires a development team" before it ever reaches the certificate. |
| `ITSAppUsesNonExemptEncryption = false` in `Info.plist` | The app ships no encryption of its own (only google_fonts' standard HTTPS, which is exempt). Without the key, App Store Connect blocks every TestFlight build on an export-compliance prompt. |
| `Disable Swift Package Manager` step in the workflow | Mirrors the proven Rextory pipeline and pins CI to the CocoaPods path that was actually verified locally. |

CocoaPods integration files (`ios/Podfile`, `ios/Podfile.lock`, and the Pods
entries in the pbxproj / xcconfigs) were generated by the first build and should
be committed.

## Secrets

Two names in the original list were wrong. The workflow reads:

| Secret | Status |
|---|---|
| `APPLE_TEAM_ID` | ✅ **already set** (`P6733MSWNR`) |
| `IOS_DIST_CERT_BASE64` | ❌ needed |
| `IOS_DIST_CERT_PASSWORD` | ❌ needed |
| `APP_STORE_CONNECT_ISSUER_ID` | ❌ needed |
| `APP_STORE_CONNECT_KEY_ID` | ❌ needed (**not** `APP_STORE_CONNECT_API_KEY_ID`) |
| `APP_STORE_CONNECT_API_KEY` | ❌ needed |
| ~~`IOS_PROVISION_PROFILE_BASE64`~~ | **not used**; the workflow downloads the profile from the portal via the App Store Connect API instead |

`karimkod/rextory` already has the five missing ones under exactly these names,
and Dotto ships from the same Apple team, so **the same distribution certificate
and the same App Store Connect API key work for both**.

The files themselves are **not on this machine**. A search of the home directory
turned up no `.p12`, no `AuthKey_*.p8` and no `.mobileprovision`, and neither
keychain holds an Apple Distribution certificate. GitHub secrets are write-only,
so the values cannot be read back out of Rextory's repo either. They were created
somewhere else (another Mac, or straight from the portal) and have to be found
there or regenerated.

```bash
# from the .p12 and .p8 files
gh secret set IOS_DIST_CERT_BASE64 --repo karimkod/dotto < <(base64 -i dist.p12)
gh secret set IOS_DIST_CERT_PASSWORD --repo karimkod/dotto
gh secret set APP_STORE_CONNECT_API_KEY --repo karimkod/dotto < AuthKey_XXXX.p8
gh secret set APP_STORE_CONNECT_KEY_ID --repo karimkod/dotto
gh secret set APP_STORE_CONNECT_ISSUER_ID --repo karimkod/dotto
```

To regenerate, use
[Certificates, Identifiers & Profiles](https://developer.apple.com/account/resources/certificates/list)
and [Users and Access → Integrations](https://appstoreconnect.apple.com/access/integrations/api).
The `.p8` API key is downloadable exactly once, so save it somewhere durable this
time.

**Create an additional Apple Distribution certificate rather than revoking the
existing one.** A team may hold more than one, and revoking the certificate
Rextory signs with would invalidate its App Store provisioning profile and break
that pipeline until the profile is regenerated. An extra App Store Connect API
key is likewise additive and disturbs nothing already in use.

## Apple portal steps

These need an interactive Apple ID login with 2FA, so they have to be done by
hand, because none of the credentials exist on this machine.

1. **Register the App ID** `com.karimkod.dotto` under team P6733MSWNR
   (Certificates, Identifiers & Profiles → Identifiers).
2. **Create an App Store provisioning profile** for it. Name it
   **`com.karimkod.dotto AppStore`**, because the workflow's `ExportOptions.plist`
   looks it up by that exact string, following the same convention as
   Rextory's `com.rextory.mobile AppStore`. Nothing needs downloading; CI
   fetches it via the API.
3. **Create the App Store Connect app record** with bundle ID `com.karimkod.dotto`,
   name **Dotto**, primary language English. Upload fails without this record
   even when signing is correct.

| `ipad-menu.png` | iPad 13" | 2064 × 2752 |
| `ipad-lvl24.png` | iPad 13" | 2064 × 2752 |

iPad shots are required because the target is universal
(`TARGETED_DEVICE_FAMILY = "1,2"`). If you'd rather ship iPhone-only, change that
to `"1"` and the iPad requirement goes away.

To regenerate: add a temporary `lib/main_screenshot.dart` that seeds
`ProgressStore` and opens either `MenuScreen` or `GameScreen` based on
`int.fromEnvironment('SHOT_LEVEL')`, then

```bash
flutter build ios --simulator --debug --target=lib/main_screenshot.dart \
  --dart-define=SHOT_LEVEL=24
xcrun simctl install <device> build/ios/iphonesimulator/Runner.app
xcrun simctl launch  <device> com.karimkod.dotto
xcrun simctl io      <device> screenshot shot.png
```

`Platform.environment` does not see simctl's `SIMCTL_CHILD_*` vars on iOS, which
is why this uses a compile-time define.

## Releasing

Once the secrets and the three portal steps are done, `pubspec.yaml` is at
`1.0.2+4` and the `v1.0.2+4` tag already exists, so the quickest path is a
manual run from the Actions tab (**iOS Release to App Store** → Run workflow)
rather than a new tag.

For subsequent releases:

```bash
git tag v1.0.3+5 && git push origin v1.0.3+5
```

The tag drives both values: `v1.0.3+5` gives version name `1.0.3` and build
number `5`. Without a `+`, the build number falls back to the GitHub run number.
App Store Connect rejects a build number it has already accepted, so use the
`build_number` input when re-running after a failed upload.
